# 分类模型路线与自蒸馏改良方案

## 1. 当前结论

项目正式分类路线统一为：

```text
BERT/RoBERTa Encoder + CNN + Attention + TF-IDF + 分类头
```

纯 BERT/RoBERTa 分类器不再作为正式路线展示或默认训练方案，仅保留为 `legacy_bert` 回滚路径。这样可以避免旧模型权重无法演示时没有兜底，同时保证报告口径不再出现“纯 BERT 和混合模型并列主线”的混乱表述。

## 2. 正式路线

### 2.1 hybrid_rankaware

默认采用路线：

```text
Tokenizer
  -> BERT/RoBERTa Encoder
  -> CNN 局部模式分支
  -> Attention 全局重点分支
  -> TF-IDF 统计关键词分支
  -> 特征拼接
  -> Dropout + Linear 分类头
  -> Softmax Top-1 / Top-3
```

训练目标采用 `RankAwareLoss`。它的核心思想是：如果真实单位已经进入 Top-3，但不是 Top-1，则降低该样本惩罚；如果真实单位不在 Top-3，则保持较高惩罚。这更贴合政务留言任务中“多单位协同、上下级转派、同条线单位均可能合理”的业务特征。

推荐参数：

```text
loss_type = rank_aware
focal_gamma = 1.5
rank_penalty = 0.25
class_weight_power = 0.6
class_weight_min = 0.5
class_weight_max = 5.0
focal_warmup_epochs = 2
best_metric = macro_f1
```

### 2.2 hybrid_self_distill

增强路线：

```text
hybrid_rankaware 主干
  + EMA teacher
  + Top-K 截断软标签
  + 动态蒸馏温度
```

软标签用于表达“类别之间不是完全互斥”的业务事实。例如同区同业务条线单位、上下级单位、同一问题链条上的单位，都可能是相对合理候选。

推荐策略：

```text
teacher_warmup_epochs = 1 或 2
distill_top_k = 5
temperature_start = 5.0
temperature_end = 1.5
hard_weight = 0.7
distill_weight = 0.3
ema_decay = 0.999
```

### 2.3 hybrid_prior_distill

长期增强路线：

```text
hybrid_self_distill
  + unit_catalog 单位目录
  + 同区/同条线/上下级/名称相似 业务先验矩阵
```

业务先验矩阵用于给真实标签以外的相关单位分配少量概率。例如：

```text
真实单位：0.85
同区同条线单位：0.05
上下级单位：0.05
名称高度相似单位：0.03
其他单位：0.02
```

这条路线最适合后续做“可解释的 Top-3 推荐”，但它依赖更规范的单位目录和单位关系治理，因此不作为第一阶段默认方案。

当前代码已提供可切换实现，训练入口参数为：

```powershell
--loss-type distillation --distill-strategy ema_bank_prior --prior-alpha 0.15 --prior-top-k 8 --prior-warmup-epochs 1
```

它会在训练启动时基于 `unit_catalog` 构建 `unit_prior_matrix.pt`，并将 EMA Soft Label Bank 的软标签与业务先验分布融合。

## 3. 代码层切换设计

运行时通过 `model_meta.json` 判断模型结构：

```json
{
  "architecture": "bert_cnn_attention_tfidf",
  "classifier_route": "hybrid_rankaware",
  "use_tfidf": true,
  "tfidf_vectorizer": "tfidf_vectorizer.joblib"
}
```

可选路线：

| 路线名 | 主干结构 | 用途 |
|---|---|---|
| `hybrid_rankaware` | BERT + CNN + Attention + TF-IDF | 当前默认正式路线 |
| `hybrid_self_distill` | 混合主干 + 自蒸馏 | 后续效果增强 |
| `hybrid_prior_distill` | 混合主干 + 自蒸馏 + 业务先验 | 长期高级路线 |
| `legacy_bert` | 纯 BERT/RoBERTa 分类头 | 回滚兜底，不作为正式方案 |

## 4. 已修正的数据处理原则

训练集与验证集必须先划分，再做以下操作：

```text
只基于训练集计算 class_weight
只基于训练集 fit TF-IDF vectorizer
验证集只能 transform，不能参与 fit
```

这样可以避免验证集信息泄漏，使 `Top-1 Acc`、`Top-3 Acc`、`Macro F1` 更可信。

## 5. 暂不采用但保留的演进方向

以下方案不作为当前阶段主线，但保留在文档中，便于后续升级或汇报时说明取舍。

### 5.1 推测解码

推测解码用于加速大模型生成。流程是：

```text
小模型快速草拟若干 token
  -> 大模型批量验证这些 token
  -> 验证通过则直接接受
  -> 验证失败处由大模型重新生成
```

暂不采用原因：

```text
1. 当前 Qwen2.5-1.5B-Instruct 规模不算特别大，生成速度尚可接受。
2. 推测解码需要额外维护小模型、草稿 token 对齐和验证逻辑，工程复杂度较高。
3. 当前系统更急需解决分类模型稳定性、RAG 命中质量和事实一致性。
```

保留价值：

```text
当后续生成模型升级到更大参数规模，或需要高并发低延迟时，可以重新评估。
```

### 5.2 更大 BGE Embedding 模型

可选模型：

```text
BAAI/bge-base-zh-v1.5
BAAI/bge-large-zh-v1.5
BAAI/bge-m3
```

暂不作为当前主线原因：

```text
1. 更大模型会增加内存和响应延迟。
2. 当前 RAG 文档规模不大，优先增加 reranker 或改进元数据过滤往往更划算。
3. 演示环境更看重稳定性和可复现性。
```

保留价值：

```text
当知识库规模扩大、政策语料更多、语义区分难度提高时，可以升级。
```

### 5.3 Reranker 二次排序 ✅ 已实现

Reranker 会把 query 和候选文档拼在一起重新判断相关性，通常比单纯余弦相似度更准。

**当前实现状态**：已集成到 RAG 检索链路

```text
BGE 稠密检索 + TF-IDF 稀疏检索
  -> 混合加权融合（默认 0.68/0.32）
  -> Cross-Encoder Reranker (BAAI/bge-reranker-base)
  -> 用户反馈加权（feedback_boost）
  -> 最终排序输出
```

**配置方式**（`configs/app/config.json`）：

```json
{
  "rag_enable_reranker": true
}
```

**效果**：
- 语义相近但业务不准的候选文档会被 reranker 降权
- 混合检索 + Reranker 后 Top-3 准确率显著提升

### 5.5 知识图谱 ✅ 已实现

知识图谱可以表达：

```text
单位上下级关系
单位职责关系
行政区/街道/社区空间关系
政策条文与案例关系
```

**当前实现状态**：已集成到 RAG 检索链路

```text
GraphAugmentor.query_related_facts()
  -> 基于查询词匹配图谱节点
  -> 获取节点属性及邻居关系
  -> 生成 RAG 兼容文档格式
  -> 注入到检索结果中
```

**配置方式**（`configs/app/config.json`）：

```json
{
  "rag_enable_graph_augment": true
}
```

**核心模块**：

| 模块 | 路径 | 功能 |
|------|------|------|
| 图谱管理器 | `src/jsjb/knowledge/graph.py` | 内存图/Neo4j 双模式 |
| 图查询引擎 | `src/jsjb/knowledge/query.py` | 高级查询和推理 |
| 结构化知识库 | `src/jsjb/knowledge/structured_kb.py` | 项目状态、单位映射 |
| 知识更新器 | `src/jsjb/knowledge/updater.py` | 从反馈自动更新 |

**效果**：
- 检索结果中会包含 `[图谱]` 前缀的知识图谱命中项
- 提供结构化的单位职责、项目状态等上下文
