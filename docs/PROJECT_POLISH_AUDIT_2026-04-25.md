## 3. 优先级最高的打磨项

## 3.1 P1：继续优化 RAG 语料与检索命中质量

### 现状

当前已经修复了排序逻辑，使“高语义相关但跨区”的案例不再被“同区但低相关”的案例无条件压制。  
同时，弱证据场景已经切换为保守回复，避免生成端乱写具体核实结论。

但从业务效果上看，还有两个明显提升空间：

- 本区高相关案例仍然不够多，导致 Top1 结果未必是最符合业务场景的案例
- 检索命中后的上下文结构还可以更贴近“政务回复生成”的需求，而不只是“语义相关”

### 建议

- 补充更多“区级 + 标签级 + 事项级”的案例
  - 例如：`朝阳区 + 环境卫生 + 垃圾清运`
  - 例如：`海淀区 + 停车秩序 + 占道停车`
- 对 RAG 语料做更细粒度字段治理
  - `issue_type`
  - `unit`
  - `district`
  - `applicable_tags`
  - `snippet`
- 建一套小型检索评测集
  - 每类典型诉求抽 20 到 50 条
  - 记录 Top1 / Top3 是否命中“可接受案例”

### 预期收益

- 提高检索 Top1 的业务相关性
- 降低生成端对弱证据兜底模板的依赖
- 让回复更自然、更贴近真实案例口径

## 3.2 P1：补齐主价值链的自动化测试

但主价值链里最关键的三块，测试仍然偏薄：

### 预期收益

- 降低后续重构把核心链路改坏的风险
- 让训练、检索、生成三块能够独立回归
- 为演示前的快速自检提供稳定工具

## 3.3 P1：训练与模型产物治理

### 现状

当前目录里保留了较多历史分类模型和训练状态：

- `checkpoints/classifier/final_model_distillation`
- `checkpoints/classifier/final_model_hybrid`
- `checkpoints/classifier/final_model_hybrid_v3_32cls`
- `checkpoints/classifier/final_model_fgm`
- `data/models/classifier/hybrid_ema_soft_label_bank`
- `data/reports/training/optuna/trials`
- `data/reports/training/optuna_trials`

这会带来几个问题：

- 占空间
- 容易混淆“哪个才是当前主模型”
- 训练脚本更容易误用旧断点或旧权重

### 建议

- 明确一个“当前主模型目录”
  - 建议以 `final_model_hybrid_v3_32cls` 为当前主线
- 给主模型目录增加一个简短说明文件
  - 训练数据版本
  - 标签体系版本
  - loss 方案
  - 是否允许续训
- 后续清理历史模型时，优先删：
  - `optuna trials`
  - 空目录
  - 非主模型的 `training_state.pt`

### 预期收益

- 降低训练与演示时的误操作概率
- 模型资产更易管理
- 更容易向导师解释“当前使用的是哪一版模型”

## 4. 第二优先级打磨项

## 4.1 P2：前端解释性还可以再增强

### 现状

前端已经能展示：

- 所属地区
- 候选单位
- 生成回复

但对“为什么是这个结果”的解释还不够强。

### 建议

- 在候选单位区域增加更明确的解释字段
  - 当前使用的分类主干
  - Top1 / Top3 的含义
  - 当前单位是“模型预测”还是“用户手动指定”
- 在 RAG 区域增加“证据强度”显示
  - `strong / medium / weak`
- 在回复区域标明当前回复模式
  - `RAG增强生成`
  - `保守兜底生成`

### 预期收益

- 演示时更容易解释系统决策过程
- 用户更容易理解“为什么这次回复比较保守”

## 4.2 P2：知识图谱链路已成型，但还偏“能力型”而非“日常主流程型”

### 现状

知识图谱目录已经较完整：

- `graph.py`
- `query.py`
- `entity_extractor.py`
- `fusion.py`
- `structured_kb.py`
- `updater.py`
- `builder.py`

但从日常主流程来看，它更像“增强能力模块”，还不是高频主路径的核心依赖。

### 建议

- 明确知识图谱的主用途
  - 是做审核
  - 是做事实结构化
  - 还是做知识补全
- 给图谱部分增加一条固定 demo 流程
  - 例如：从一条留言中提取事实 -> 进入审核候选 -> 审核通过后入库
- 增加 1 到 2 个“可视化解释示例”

### 预期收益

- 知识图谱能力更容易在汇报中讲清楚
- 减少“功能很多但主线角色不明确”的感觉

## 4.3 P2：运行日志与质量日志可以再分层

### 现状

当前已有结构化日志，但从运维角度还可以再区分：

- 运行日志
- 质量日志
- 训练日志

### 建议

  - 例如串区、弱证据、事实验证告警

- 让 `/api/analyze` 支持更细的 debug 开关
  - 仅在开发环境输出更多中间信息

### 预期收益

- 更容易定位效果问题
- 更适合做后续主动学习与语料补强

## 5. 第三优先级打磨项

## 5.1 P3：清理 `__pycache__` 与历史测试缓存

### 现状

当前 `src/` 和 `tests/` 下仍可见不少 `__pycache__` 和 `.pyc` 文件。

这类文件不影响运行，但会让目录显得嘈杂，也容易干扰项目盘点。

### 建议

- 清理项目内已有 `__pycache__`
- 确认 `.gitignore` 已覆盖：
  - `__pycache__/`
  - `*.pyc`

### 预期收益

- 目录更干净
- 后续文件盘点更准确

## 5.2 P3：整理 `legacy/` 的说明，而不是急着删除

### 现状

`legacy/` 本身体积很小，保留成本不高。

### 建议

- 保留 `legacy/`
- 但在目录下补一份 `README`
  - 标明哪些文件只是历史备份
  - 标明不参与当前主流程

### 预期收益

- 保留回溯价值
- 又不至于误导后续维护者
