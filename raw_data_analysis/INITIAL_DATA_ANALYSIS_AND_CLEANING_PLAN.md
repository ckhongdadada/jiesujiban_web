## 二、字段结构结论

大多数区级原始工作簿字段结构高度一致，核心字段为：

- `留言人名称`
- `留言Id`
- `留言时间`
- `留言标签`
- `发生地`
- `留言标题`
- `留言正文`
- `官方回复单位`
- `官方回复时间`
- `官方回复正文`

爬虫总表在上述基础上额外包含：

- `留言来源`

城市级工作簿（市委书记、市长留言板）有一个重要差异：

- 有 `官方回复正文`
- 没有 `官方回复单位`

这意味着它们适合做 `地名识别` 和 `回复生成`，但**不适合直接做“官方回复单位分类”的监督样本**。

## 三、合并后总体画像

### 1. 面向地名识别（NER）

可用样本：`21957` 条

关键观察：

- 含明显地点提示词的留言有 `18988` 条，占比 `86.48%`
- 留言文本平均长度 `165.41` 字，`P95=421`
- `发生地` 字段非空仅 `1656` 条，占比 `7.54%`

结论：

- `标题 + 正文` 本身已经是很强的地点挖掘语料。
- `发生地` 字段虽然覆盖率不高，但质量很好，能作为高价值弱监督标签，用于地点词典构建、别名归并和地名抽取校验。
- 不能只依赖 `发生地` 做 NER 监督，因为覆盖太低；应该把它作为“高精度补充信号”。

### 2. 面向官方回复单位预测

可用样本：`17091` 条

关键观察：

- 唯一单位数：`1011`
- 样本数 `<2` 的单位：`396`
- 样本数 `<5` 的单位：`638`
- 重复问题键仅 `3` 条
- 同一问题对应多个单位：`0`

结论：

- 监督一致性很好，同一留言基本不会对应多个回复单位。
- 但标签长尾非常严重，直接拿 `1011` 类做平铺分类会导致训练很吃力。
- 当前原始单位字段里混有明显伪标签或平台标签，如 `@北京12345`，这些不能直接作为真实承办单位类别。

### 3. 面向官方回复生成

可用样本：`21698` 条

关键观察：

- 有回复单位的样本：`17091`

- 命中“低信息量进度通知”规则：`720`
- 命中“现场核查否认投诉”规则：`1062`
- 回复平均长度：`241.19` 字，`P95=548`

结论：

- 这份初始数据足够支撑回复生成训练。
- 但模板化回复、转办型回复、否认型回复占比不低，如果不做治理，模型会学到大量空泛官话或与诉求不一致的答复模式。

## 四、这批初始数据最值得注意的质量问题

### 1. 标签结构不统一

`留言标签` 在不同来源中存在两种形态：

- 区级原始工作簿：更接近普通标签
- 爬虫总表：大量是字符串化三元组，例如 `(' 投诉/求助 ', '城建', '已办理')`

影响：

- 不适合直接原样喂给分类或生成模型
- 会让模型把“结构噪声”学成文本特征

### 2. 回复单位字段噪声重

高频单位中出现了：

- `@北京12345`
- `认领交办`
- 行政区名本身，如 `通州区`
- 平台/热线中心名

影响：

- 这些值并不都等价于“真实承办单位”
- 会破坏单位分类标签空间

### 3. 城市级数据缺失回复单位

以下两份数据有回复正文但没有回复单位：

- `北京市委书记尹力留言板.xlsx`
- `北京市市长殷勇留言板.xlsx`

影响：

- 能做生成
- 不能直接做单位分类

### 4. `发生地` 字段覆盖率低但价值高

虽然只有 `7.54%` 的留言填写了 `发生地`，但字段内容往往非常具体，例如：

- 精确到区、街道、胡同、路口
- 精确到小区、地铁站、医院、公园等 POI

影响：

- 非常适合做地名词典和地址别名库的高精度来源
- 不适合单独作为训练集唯一地点标签

### 5. 跨来源重复存在，但不严重

- 重复问题键总数：`13`
- 重复问题+回复组合：`7`
- 跨源文件重复问题：`3`

影响：

- 合并时仍然需要做去重
- 但重复规模不算大，说明原始源之间并没有大量完全重叠

## 五、面向三个任务的统一清洗方案

目标不是做三套互相割裂的数据，而是先做一层“标准化母表”，再按任务切分子集。

### 第一步：建立统一母表

建议统一字段如下：

- `record_id`
- `source_file`
- `source_sheet`
- `source_type`：`district_raw / city_raw / crawler_raw`
- `district_from_file`
- `message_source`
- `message_id`
- `message_time`
- `message_tag_raw`
- `message_tag_level1`
- `message_tag_level2`
- `message_status`
- `message_location_raw`
- `message_title`
- `message_body`
- `message_text`
- `reply_unit_raw`
- `reply_unit_norm`
- `reply_time`
- `reply_text_raw`
- `reply_text_clean`
- `dedupe_issue_key`
- `dedupe_generation_key`

### 第二步：统一做的标准化处理

#### A. 字段名统一

把不同来源中的同义字段全部映射到统一字段名。

#### B. 空白字符和异常字符清理

处理：

- 全角/半角空格
- 多余换行
- 制表符
- 前后缀空白
- 平台爬虫残留符号

#### C. 标签字段结构化

将 `留言标签` 拆成三个层次：

- `message_tag_level1`：如 `投诉/求助`、`咨询`、`建言`
- `message_tag_level2`：如 `城建`、`交通`、`教育`
- `message_status`：如 `已办理`

如果原字段不是元组字符串，就走规则映射或保底填充。

#### D. 回复单位归一化

建立 `reply_unit_norm` 规则表，至少做四类处理：

1. 去空白、去换行、去前后缀符号
2. 识别并剔除平台型值，如 `@北京12345`
3. 识别并单独标记流程状态值，如 `认领交办`
4. 合并同义单位、简称和全称

#### E. 去重键构建

建议至少保留两种去重键：

- `dedupe_issue_key = 标签 + 标题 + 正文`
- `dedupe_generation_key = 标签 + 标题 + 正文 + 清洗后回复`

## 六、针对三个任务的子集方案

### A. 地名识别训练集

保留条件：

- `message_title` 或 `message_body` 非空
- 优先保留 `message_location_raw` 非空样本
- 同时保留没有 `message_location_raw` 但正文中存在明显地点提示词的样本

建议加工：

1. 从 `message_location_raw` 中提取高置信度地点别名
2. 从 `message_text` 中挖掘高频地点候选
3. 用地点类型拆词典：
   - 行政区
   - 街道/道路
   - 小区
   - 地铁站
   - 公交站
   - 医院/学校/公园/商场
4. 构建 `mention -> 标准地名 -> 行政区 -> 地点类型` 映射表

这部分最关键的不是“删多少”，而是：

- 高精度字段 `发生地` 作为正样本来源
- 正文里的海量地点提及作为扩充来源
- 后续与现有高德/词典体系对齐

### B. 官方回复单位分类训练集

保留条件：

- `message_text` 非空
- `reply_unit_norm` 非空
- 排除平台型伪单位和流程型伪单位

建议处理：

1. 删除或单独标记以下类别：
   - `@北京12345`
   - `认领交办`
   - 空值
   - 只表示区名但不表示承办部门的值
2. 做单位同义归并，例如：
   - 委 / 委员会
   - 局 / 管理局
   - 街道 / 办事处
3. 对长尾类别设置阈值：
   - 极低频单位先合并到上级类别
   - 或做“一级单位大类 + 二级精细单位”的层级分类
4. 保留 `district_from_file` 与 `message_tag_level2` 作为辅助特征

建议最终产出两套标签：

- `unit_label_coarse`：粗粒度主管条线/部门大类
- `unit_label_fine`：细粒度承办单位

这样可以同时满足：

- 当前分类模型先跑稳
- 后续再升级到更细粒度标签

### C. 官方回复生成训练集

保留条件：

- `message_text` 非空
- `reply_text_raw` 非空

建议处理：

1. 对回复正文做公文清洗：
   - 去抬头
   - 去问候语
   - 去“您于某年某月某日反映……”引导段
   - 去落款、日期、套话尾巴
2. 剔除或降权：
   - 低信息量进度通知
   - 纯转办类回复
   - 现场核查否认类回复
3. 对模板化高重复回复做降采样
4. 若 `reply_unit_norm` 可用，则加入条件字段；若不可用，也保留作“无单位条件生成”样本
5. 将 `message_tag_level1 / level2 / district_from_file / 预测区县` 作为结构化提示输入

建议最终生成训练样本分两层：

- 高质量核心集：信息密度高、办理结果明确、模板味弱
- 扩展训练集：覆盖面更广，但训练时降低采样权重

## 七、推荐的数据产物

建议最终不要只生成一个清洗后的大表，而是同时产出：

1. `master_clean.parquet`
   - 统一母表，保留最完整字段
2. `ner_training_candidates.parquet`
   - 地名识别候选集
3. `unit_cls_training.parquet`
   - 官方回复单位分类集
4. `reply_gen_training.parquet`
   - 官方回复生成集
5. `reply_unit_mapping.csv`
   - 单位归并映射表
6. `tag_mapping.csv`
   - 标签结构化映射表
7. `location_alias_seed.csv`
   - 从 `发生地` 和正文中提取的高置信度地点种子表

## 八、优先级建议

如果我们下一步开始真正做清洗，我建议顺序是：

1. 先做统一母表
2. 再做 `留言标签` 结构化
3. 再做 `回复单位` 归一化与伪标签清除
4. 然后抽取 `发生地` 和正文中的地点种子
5. 最后分别切出三套训练子集

这样做的好处是：

- 一次治理，三条链路共用
- 后续 NER、分类、生成都能从同一母表回溯到原始来源
- 以后新增数据时也能复用同一套标准化流程
